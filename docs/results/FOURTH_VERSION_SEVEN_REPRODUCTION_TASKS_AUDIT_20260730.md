# 第四版七个论文复现任务人工评估与版本对比

## 结论摘要

第四版的七个任务均正常启动并完成，但“任务完成”不等于“论文结论完整复现”。按 `dual_axis_100` 规则人工复核后，七个任务的平均科学结论分为 62.86，平均科研过程分为 76.43，平均最终分为 52.01。自动 Judger 的平均最终分为 53.56，人工复核比自动评分低 1.55 分。

工具层改造总体有效：297 次 Chemistry MCP 调用中 286 次成功，接口表面失败率为 3.70%；137 次预设 Action 调用中 134 次成功，排除两个非法请求后后端成功率为 99.26%；16 个原生 GoodVibes 作业全部成功。真实混合搜索共 18 次，全部启用语义检索，Top-1 均与查询科学意图相关。GEOM 任务的 12 个 ORCA 优化和 12 个 Hessian 作业已真实并行运行，且 `r2SCAN-3c` 未再错误生成 `AUTO` 关键字。

当前主要瓶颈已经从 Action 和原生软件层转移到通用编程接口与科学路线判断：20 个实际启动的 Python 分析作业只有 10 个成功，另有 5 次提交在预检阶段被拒绝；`PV_Protonation_Barrier_Trend_Reproduction`、BaO 和 GEOM 的程序重试造成了明显 token 浪费。Heterobiaryl 两个任务的核心问题不是软件执行失败，而是智能体没有把作者文件角色正确映射到评估所需的反应路径，或错误解释论文的决速步骤。

| 层级 | 第四版真实结果 | 判断 |
|---|---:|---|

| 预设 Action | 134/137 成功；2 个非法解析请求、1 个 GoodVibes 后端失败 | 整体可用率 97.81%；排除非法请求后后端成功率 99.26% |

| 通用 Python 作业 | 10/20 成功、10/20 失败；另有 5 次预检拒绝 | 当前最严重的执行可靠性问题；按 25 次提交意图计算只有 40% 最终成功 |
| JobContext | 20 个已启动程序中 17 个完整合规、3 个部分合规 | SDK 采用率明显提高，但采用 SDK 并未自动消除脚本逻辑和文件解析错误 |
| 非托管 Python | 轨迹中检测到 30 次 shell Python 使用 | 仍会削弱统一产物合同、lineage 和失败审计 |

第四版的 Action 后端不是主要失败来源。137 次 Action 中，ORCA 优化与 Hessian、VASP 能量与弛豫、电子密度和等值面计算均稳定完成。失败集中在以下位置：

- GEOM：6 个分析程序作业中 4 个失败，主要是路径和脚本逻辑问题。
- BaO：6 个分析程序作业中 5 个失败，最终 EOS 分析存在手工写入能量数据的过程风险。
- PV：5 次分析程序提交全部在预检阶段失败，之后使用了 18 次非托管 shell Python；另有数组读取上限、GoodVibes 参数和模块检查问题。
- Heterobiaryl 02：程序执行本身成功，但反应路径文件角色解释错误，属于科学数据映射失败。

## 并行与 ORCA 适配修复

GEOM 是第四版批量异步 Action 的直接验收任务：

- 12 个 `optimize_geometry` 在约 0.04 秒内全部提交，每个使用 4 CPU，合计覆盖 48 CPU。
- 12 个 `calculate_hessian` 在约 0.06 秒内全部提交，同样覆盖 48 CPU。
- 24 个 ORCA 作业全部完成，没有因同步 Action 串行阻塞。
- ORCA provenance 中方法为 `r2SCAN-3c`，实际命令为 `orca ./job.inp`，没有出现错误的 `AUTO` 基组关键字。
- 相对第三版 GEOM，运行时间从 2,937.7 秒下降到 1,789.6 秒，下降 39.1%；工具非成功从 10/54 降到 2/70；自动最终分从 75 提升到 90。

因此，预设 Action 无法并行和 `r2SCAN-3c + basis=auto` 的两个第四版目标均已在真实轨迹中通过验证。

- `PV_Protonation_Barrier_Trend_Reproduction` 比第一版增加 97.4%，原因是反复尝试程序提交、解析、GoodVibes 组合和大量非托管 Python。

## 版本判断

第四版相对前几版的客观改善包括：七个任务全部启动并完成；语义检索在真实 Agent 环境中 100% 可用；Action 后端成功率接近 100%；原生作业无终态失败；discovery 返回量显著下降；批量异步 Action 和 ORCA 方法适配修复得到真实验证。

尚未达到预期的部分包括：通用 Python 作业终态失败率仍为 50%；非托管 Python 使用较多；PV 的热化学组合没有形成可靠的托管工作流；Heterobiaryl 文件 manifest 解决了频率/DLPNO/QZ 技术配对，但没有让智能体可靠完成“作者命名到反应路径”的科学映射；部分任务虽然工具执行成功，最终科学路线仍然错误。

按人工最终分比较，第四版七任务平均 52.01，第一版相同七任务平均 50.56，只提高 1.45 分。基础设施可靠性和执行效率已经明显改善，但总体科学评分提升很小，原因是 PV 和两个 Heterobiaryl 任务仍被科学数据解释与路线判断限制。下一轮最值得优先解决的不是 Action 后端，而是通用分析程序模板/预检、托管能量组合，以及不泄露结论的反应路径角色验证工具。
